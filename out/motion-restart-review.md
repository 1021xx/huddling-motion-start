## 진단
기존 타임라인은 5초짜리 독립 composition 세 개다. 첫 장면의 폰 등장은 0–0.24초, 카드 등장은 0.24–0.48초, 퇴장은 4.85초부터다. 따라서 첫 장면에는 주요 등장 완료 후 약 4.37초의 정적 구간이 있다. 프레임에서도 폰 왼쪽/설명 오른쪽 구도가 세 장면에 반복된다.

기존 REFERENCE.md는 실제 영상 대신 Apple-style rise 프롬프트와 Carbon UI 모션 문서를 근거로 삼았고, 상승·감속·폰 정착 후 카드 등장·하강 시차를 평가했다. 이 평가를 통과하는 것과 영상의 리듬·연속성·타이포 연출이 좋은 것은 별개다.

현재 모션 규칙은 작은 UI 상태 변화에 적합하지만 영상 편집의 표현 범위는 좁다. 고정 카메라, 짧은 wrapper 이동, 확대/회전 미정 상태를 그대로 기본 패턴으로 반복한 것이 문제다. 토큰 준수만을 영상 품질로 간주하지 않는다.

## 참고 영상에서 확인한 사실
시간은 관찰 구간이며 정확한 컷 경계가 아니다.

| 구간 | 확인한 표현 | 이번 작업에 적용할 원리 |
|---|---|---|
| 0–3초 | 문구가 먼저 보이고 파란 강조 문구·아이콘·폰이 순차 등장 | 처음부터 완성 화면을 모두 공개하지 않고 시선의 순서를 설계 |
| 약 3–5.5초 | 미션 카드/캐릭터/제출 영역으로 구도 변화, 제출 영역이 커짐 | 전체 UI와 행동 부분의 크기 차이로 초점 이동 |
| 약 5.5–6.7초 | 종이비행기가 이동하고 커지며 화면을 가로지름 | 앞 행동이 다음 컷으로 이어지는 전환 동기 부여 |
| 약 6.7–8초 | 검은 바탕의 짧은 ‘승인?’과 큰 체크 결과 | 짧은 질문과 결과의 대비로 리듬 전환 |
| 약 9–13초 | 자산 카드 교체 후 판매 문구와 수익 수치 변화 | 같은 자리에 연속 정보를 이어 보여주는 방식 |

참고의 검은 배경, 종이비행기, 수익 정보는 현재 서비스 룩/자산/미션 범위와 자동으로 합치지 않는다. 가져올 대상은 시선 이동과 장면 연결 방식이다. 참고 영상 자체가 복잡한 키네틱 타이포의 완성 기준인 것은 아니며, 더 적극적인 타이포는 이번 사용자 요청에 따른 새로운 연출 제안이다.

## 개편 제안 — 아직 확정 장면표 아님
기존 15초/1920×1080/30fps/밝은 배경을 출발점으로 사용한다. 약 1초를 편집 박자의 기준으로 삼되, 모든 화면을 기계적으로 1초에 자르지 않는다. 한 박자에는 짧은 단어 또는 한 행동만 배치하고 결과 문구에는 더 긴 읽기 시간을 준다.

| 제안 구간 | 시선과 연결 방식 |
|---|---|
| 0–3초 | ‘이번 달’ → ‘미션’ → ‘도전’. 단어가 순차 교체되고 남은 ‘미션’이 실제 미션 카드 제목 위치로 연결된다. |
| 3–6초 | 카드 전체 → 핵심 내용 → ‘결과물 + 적용 사례’. 같은 카드/정렬축을 유지하면서 초점을 좁힌다. |
| 6–9초 | ‘제출’ 단어를 기존 제출 버튼과 정렬해 연결. 버튼 반응 이후 ‘검토 후’로 넘어가 즉시 자동 승인이라는 오해를 막는다. |
| 9–12초 | ‘승인’ 문구와 원본 승인 배지를 연결하고 승인 화면의 자산 영역으로 시선을 옮긴다. |
| 12–15초 | ‘내 자산으로’라는 결과를 읽을 시간과 원본 로고로 마무리한다. |

타이포 기법: 고정 단어+교체 단어, 글줄 마스크 리빌, 문구와 UI 라벨의 위치 연결. 모든 컷에 같은 기법을 반복하지 않는다. 새 확대율/이동량/마스크 연출 수치는 아직 채택하거나 구현하지 않았다.

## 다음 제작에서 검증할 항목
- 각 전환에서 무엇이 남고 무엇이 다음 초점으로 바뀌는지 설명할 수 있어야 한다.
- 주요 문구/행동이 1초 박자에 읽히는지 실제 재생으로 확인한다.
- 같은 상하 등장 패턴과 같은 구도가 연속 반복되지 않아야 한다.
- 정지 프레임의 예쁨과 별개로 전환 전후 연속 프레임을 검수한다.
- 기존 색/폰트/로고/UI 원본을 보존하고, 별도 타이포 연출 규칙은 UI 피드백 규칙과 구분한다.

## 상태
분석과 개편 제안만 작성했다. 원본 프로젝트/MD/영상은 변경하지 않았다. 기존 mission-entry-focus 스냅보드는 승인되지 않은 기록이 있으므로 새 제안이 승인된 것으로 취급하지 않는다. 사용자의 이번 메시지도 새 수치 또는 완성 시안의 승인으로 기록하지 않는다.
